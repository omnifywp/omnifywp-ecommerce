# Taste
- Works primarily in a WordPress plugin codebase (PHP 8.2) and expects code to comply with WordPress Coding Standards / PHPCS: input sanitization, output escaping (`esc_html`/`esc_url`/`esc_js`), nonces for state-changing/export actions, and `$wpdb->prepare()` for raw SQL. Confidence: 0.7
- Uses tab indentation in PHP and JS. Confidence: 0.7
- Follows WordPress global-namespace hygiene: `omnify_`-prefixed function names and `$omnify_`-prefixed local variables/parameters. Confidence: 0.7
- Cares about internationalization: user-facing strings (including in inline JS) should be translatable via `__()`/`esc_html__()`/`esc_js()` with the plugin text domain, not hardcoded English. Confidence: 0.6
- Prioritizes security hardening (signature/HMAC verification, nonce protection, credential handling, IP normalization, input sanitization) as the top tier of remediation work, followed by data-integrity, then storefront/analytics, then performance. Confidence: 0.6
- Values performance-conscious code (avoiding N+1 query cascades, replacing O(N²) algorithms with pre-indexed O(N) approaches). Confidence: 0.5
- Works in a no-build-step environment: client-side JS assets are authored as plain vanilla/ES5 scripts that consume the global `wp.*` APIs (wp-blocks, wp-element, wp-components, etc.) rather than being bundled (no webpack/babel/JSX). New front-end/editor JS should follow the same convention. Confidence: 0.5
- For Gutenberg blocks, expects a real block editor UX: editor previews visually match the front end (load the scoped front-end storefront CSS in the editor too), and every block exposes customization via inspector controls backed by real attributes that actually change rendering. Confidence: 0.7
- Prefers design consistency via shared store-level design tokens (CSS variables for primary/hover color, border radius, font family) applied uniformly to every block and to the editor preview, instead of hardcoded per-component colors/radii/fonts. Confidence: 0.6
- Wants a broad, expansive customization surface on components/blocks (many options: layout, columns, toggles, labels, content visibility, plus style controls for colors, typography, spacing, borders, shadow, and alignment) rather than a minimal set; repeatedly asks to "add more" customization features and to "improve all the blocks" with more options at once. Confidence: 0.7
- Judges styling features by their visible effect on the rendered front end: block style controls (background, text color, font size, radius, alignment) must actually win over the theme/storefront's scoped `!important` CSS rather than only landing on an outer wrapper, and they report it bluntly/tersely ("style customization isn't working", "still now ... isn't working") when they don't. They also treat a feature as broken when its controls aren't discoverable — a Style panel that only rendered last-and-collapsed read to them as "no Style panel at all", so important controls should be prominent (first, expanded by default). Confidence: 0.6
- Prefers shared, uniform control surfaces across all blocks/components (e.g. one common "Style" panel and one shared set of style attributes merged into every block) rather than bespoke per-block styling code. Confidence: 0.5
- Treats the shipped plugin code + README as the source of truth for documentation: wants docs/website kept in sync with actual features and prefers correcting factual inaccuracies (wrong counts, nonexistent gateways/providers) over preserving stale wording. When asked to "update docs," they expect a full sweep across every doc artifact (markdown docs, static HTML site, and generated pages) rather than a partial update. Confidence: 0.5
- Accepts forward-looking / aspirational documentation alongside code-faithful content: when offered the choice, they allow documenting planned features and best practices even when not yet implemented, rather than restricting docs to only what ships today. Confidence: 0.5
- For large documentation work, issues very terse high-level directives ("extend the doc") and, when given scope options, selects all of them at once — prefers maximal coverage (developer docs, merchant how-tos, more recipes, complete REST/hook references) over a narrowly scoped addition. Confidence: 0.5
- Prefers non-destructive, opt-in overrides: unset/default option values fall back to the store's global defaults (e.g. tri-state "Use store default / Show / Hide", radius `-1` = inherit) instead of clobbering global settings, and no extra wrapper markup is emitted when everything is left at default. Confidence: 0.5
